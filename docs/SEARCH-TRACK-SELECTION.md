# Search & Track Selection

Начиная с `v0.12.0`, Baskov Discord Bot поддерживает отдельную команду `/search` для осознанного выбора результата YouTube.

## Пользовательский сценарий

```text
/search green day holiday
→ до пяти результатов с названием, автором, длительностью и провайдером
→ кнопки 1–5
→ выбранный трек запускается или ставится в текущую очередь
```

`/play` остаётся быстрым сценарием: он сразу берёт первый подходящий результат. `/search` нужен, когда важно выбрать официальную запись, live-версию, кавер или конкретную длительность.

## Безопасность component IDs

Каждый поиск создаёт случайный token и короткоживущую in-memory session:

- session привязана к Discord guild ID;
- session привязана к Discord user ID;
- доступно не более пяти кандидатов;
- срок жизни — пять минут;
- успешный выбор атомарно удаляет session;
- повторное нажатие той же кнопки не добавляет дубликат;
- чужой пользователь не может выбрать или отменить результат.

В component ID не помещаются названия, URL или внутренние данные трека — только token и позиция результата.

## Voice и очередь

Поиск не подключает бота к voice и не создаёт музыкальную session. Voice-проверка выполняется только после нажатия кнопки выбора через ту же `MusicControlPolicy`, что и `/play`.

Выбранный `AudioTrack` уже загружен modern YouTube source. `PlayerManager.queueLoadedTrack(...)` передаёт его в `TrackScheduler` без повторного network lookup. Это исключает расхождение между показанным и реально добавленным результатом.

## Отказы

- пустой результат → понятный `Ничего не найдено`;
- ошибка YouTube source → `Поиск временно недоступен`;
- истёкшая или уже использованная session → кнопки очищаются;
- отсутствие voice-доступа → session не расходуется до проверки policy;
- ошибка voice connection после claim → пользователю показывается стандартная voice diagnostics ошибка, повторный поиск требуется явно.

## Ограничения

Search sessions хранятся только в памяти процесса и намеренно не переживают restart контейнера. Это безопасная временная UI-state, а не продуктовые данные.


## Search & Discovery 2.0 (v1.4.0)

`/discover` продолжает существующий безопасный `/search`, не создавая второй путь загрузки треков:

- `/discover recent` — до 10 последних запросов текущего пользователя;
- `/discover again` — повтор последнего интерактивного поиска;
- `/discover related` — текстовый YouTube-поиск по `author + title` текущего трека;
- `/discover history position:<N>` — такой же контекстный поиск по записи из `/history`.

`related` — это **не ML-рекомендация и не обращение к персонализированному API YouTube**. Команда только формирует новый текстовый запрос из уже известных метаданных трека и передаёт его в тот же `MediaQueryResolver` + `PlayerManager.search`, поэтому сохраняются прежние ограничения прямых URL, пять кандидатов, TTL и одноразовый claim результата.

Autocomplete `/play query` и `/search query` теперь локально объединяет: in-memory недавние запросы пользователя, persistent playback history сервера и треки постоянных плейлистов. Результаты дедуплицируются без учёта регистра, фильтруются по вводимому тексту и ограничиваются Discord-лимитом 25 choices. Во время autocomplete сетевые запросы к YouTube не выполняются.
